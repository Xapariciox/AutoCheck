## Project status

AutoCheck is a vehicle preventive-maintenance app (traffic-light health status + immutable digital service passport). As of Sprint 1 (Oct 2026) `backend/`, `mobile/` and `docs/` exist only as placeholder folders (no Spring Boot or Expo project yet); the layout, commands and conventions below are the **planned** design from the README. When scaffolding `backend/` or `mobile/`, follow that design; once real code exists, trust the code over this file and update it. The README and team communication are in Spanish — keep docs, commit descriptions and user-facing strings in Spanish.

## Monorepo layout

- `backend/` — Java 21, Spring Boot 3, Maven (`mvnw` wrapper committed), PostgreSQL 16 + Flyway.
- `mobile/` — Expo + React Native + TypeScript (strict). `ios/` and `android/` are generated by `expo prebuild` and gitignored — don't edit them by hand.
- `docker-compose.yml` — backend, PostgreSQL, pgAdmin (:5050), Mailpit (:8025). Env from `.env` (copy `.env.example`).
- `.github/workflows/ci.yml` — path-filtered jobs; `ci-ok` is the required final check.

## Commands

```bash
# Full stack
docker compose up -d --build              # API at :8080/api/v1, Swagger at /swagger-ui.html

# Backend without Docker
docker compose up -d db
cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
cd backend && ./mvnw verify               # all tests + JaCoCo (Testcontainers → needs Docker running)
cd backend && ./mvnw test -Dtest='*Health*'          # calculation-engine tests
cd backend && ./mvnw test -Dtest=ClassName#method    # single test

# Mobile
cd mobile && npm ci && npx expo start
cd mobile && npm test                     # Jest (@swc/jest) + RNTL + MSW
cd mobile && npx jest path/to/file.test.tsx -t "name" # single test
cd mobile && npm run lint && npx tsc --noEmit
cd mobile && maestro test .maestro/       # E2E on Android emulator
```

Coverage targets: backend ≥ 70 %, health/calculation engine ≥ 90 %, mobile ≥ 60 %.

From the Android emulator the API is `http://10.0.2.2:8080`; on a physical device use the host's LAN IP. Set via `EXPO_PUBLIC_API_URL`.

## Architecture

- **All calculation logic lives in the backend** (single source of truth, tested with JUnit). The mobile app only renders results — never reimplement the traffic-light/projection math on the client.
- Backend modules by domain: `auth · vehicle · odometer · health · checklist · passport · legal · notification`, each with `controller`, `service`, `repository`, `dto` packages and its own tests. MapStruct + Lombok for DTO mapping; JWT access + refresh tokens; `@Scheduled` jobs for ITV/insurance deadlines and push via Expo Push Service.
- Mobile: React Navigation, TanStack Query + Axios (offline-first cache) in `src/api/`, Zustand in `src/store/`, React Hook Form + Zod for forms, tokens in Expo SecureStore. Feature code under `src/features/<domain>`.
- Invoice photos never leave the device; the backend stores only their hash.
- **API contract first:** endpoints are agreed in OpenAPI at sprint start; mobile develops against MSW mocks of that contract.

### Health engine (traffic light)

Each consumable expires by km **or** time, whichever comes first:

```
km_today       = km_last_reading + days_since_reading × daily_avg
usage          = max((km_today − km_last_change) / interval_km, days_since_change / interval_days)
days_remaining = min(km_remaining / daily_avg, last_change_date + interval_months − today)
```

- Green: usage < 0.80. Yellow: 0.80 ≤ usage < 1.00, or < 30 days remaining, or ITV < 30 days, or insurance < 45 days. Red: usage ≥ 1.00, critical checklist failure, or ITV/insurance expired. Grey: no initial data.
- Global status = worst of all.
- `daily_avg` = weighted average of the last 3 real readings (50/30/20 %); with a single reading, use the usage profile (urban 20, mixed 35, highway 70 km/day).
- Default intervals per fuel type (gasoline/diesel/hybrid/electric) are seeded via Flyway into `maintenance_rule`; users can override per vehicle in `vehicle_consumable`. The full table is in the README.

### Passport immutability

- `service_record` is insert-only: a PostgreSQL trigger rejects `UPDATE`/`DELETE`. Corrections are new records pointing to the voided one via `voided_record_id`.
- Records form a SHA-256 hash chain (`prev_hash`, `hash`). PDF reports (OpenPDF) are signed with HMAC-SHA256 (`PASSPORT_HMAC_SECRET`) and include a ZXing QR for public verification.
- Checklist Gatekeeper: the fluids checklist is blocked if the engine has been off for < 2 hours.

## Conventions

- **Flyway migrations** are timestamp-named to avoid cross-branch collisions: `V20261021_1530__crear_tabla_vehicle.sql`. Never edit a migration that has been merged.
- **Branches:** `feature|fix|chore|docs/T-xx-descripcion` — one Trello card = one branch = one PR. `main` is protected (PR + 1 approval + green CI, squash merge). Rebase on `origin/main` rather than merging.
- **Commits:** Conventional Commits with scope and card code, e.g. `feat(backend): registro y login con JWT [T-08]`.
- **PR titles:** `[T-08] Registro y login con JWT`, linking the Trello card (board: https://trello.com/b/x3jAlwSn/autocheck-proyecto-final; card prefixes [BE], [MB], [OPS]).
